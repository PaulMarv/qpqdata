# Phase 2E — Dataset library and free downloads

## Publication policy

Approval and payout do not authorise public distribution. Migration 0008 creates no publications, consents, members or exports for existing records. An owner must explicitly authorise public publication of a frozen collection, review its descriptions/licence/reuse terms and choose the metadata fields that may be public. Each contributor must separately opt in for each image, and the owner must separately review and authorise that approved image for export. Pending, rejected, hidden, deleted, withdrawn, unconsented and unauthorised images cannot enter an export. An active removal request also blocks export even if its hidden flag was not set through the UI.

The owner policy is frozen. It binds the project/criteria version, canonical licence, recorded reuse terms and selected public question keys through an immutable digest. Contributor consent records bind that digest, the original immutable submission licence/terms, contributor identity, explicit public-distribution statement, timestamp and optional public pseudonym. These private audit records are not exported. Owner export review requires current verified, eligible authentication and ownership; collection moderation permission alone cannot publish a dataset or authorise distribution. Contributor opt-in alone is also insufficient.

Supported licences are CC0-1.0, CC-BY-4.0 and CC-BY-SA-4.0. Empty/custom licences fail closed pending separately designed rights review. BY/BY-SA require a deliberately supplied public attribution pseudonym; account display names/emails are never substituted. The original licence and reuse terms must match the consent and frozen collection. Owner/contributor attestations are explicit rights decisions; software does not interpret arbitrary prose as a legal permission or prove originality, suitability or third-party rights. Do not confirm publication if original restrictions prohibit distribution.

Images, image labels and selected single-choice, multiple-choice, number and yes/no answers may be public. **Free-text answers remain private in Phase 2E**, including in the exported criteria schema. Owners must review even coded metadata for privacy. This is an intentional bounded metadata-publication policy, not an assertion that all structured answers are anonymous. Public project descriptions/schema are explicitly reviewed by the owner. Consent withdrawal or owner image-authorisation withdrawal stops further distribution without deleting the original image or changing QC; it is terminal for that consent. Whole-dataset withdrawal is terminal for its publication policy. No automatic reactivation or widening of a frozen policy occurs.

Creative Commons guidance and canonical legal terms are linked from the UI and ZIP. See [CC0 legal code](https://creativecommons.org/publicdomain/zero/1.0/), [BY 4.0](https://creativecommons.org/licenses/by/4.0/) and [BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/). The full standard texts bundled in `app/resources/licences/` were retrieved from the [SPDX official licence catalogue](https://github.com/spdx/license-list-data/tree/main/text), after the Creative Commons host rejected direct programmatic downloads. There is no network licence lookup during export generation.

## Library and contributor/owner UI

- Public `/datasets` offers search by name, keyword, collection ID or dataset ID; category/licence filters; newest, updated and relevance ordering; server-side pagination and responsive cards. Only explicit, active publication records are listed. An authorised publication can initially have zero downloadable images.
- `/datasets/<dataset UUID>` shows purpose, description, collection identifier, labels, selected schema, criteria version, licence/reuse guidance, immutable versions, readiness and free download controls. `image_count` describes the most recent usable published manifest, not every approved collection submission. New approvals do not silently alter it.
- **My Collections → Dataset publication** lets owners create the policy, inspect opted-in approved images/selected answers, separately authorise them, publish the current set as a version, withdraw permissions and review public reports.
- **My Submissions → Optional public dataset distribution** lets the contributor read the exact public fields/licence, supply a public pseudonym, opt in and later withdraw further distribution. Opt-in affects neither submission moderation status nor earned QC.
- Guest and signed-in downloads cost **0 QC**. The UI asks users to read the licence/reuse terms before enabling a download; the licence is public and the backend does not use a credit balance as an access condition.

## Immutable versions and ZIP contents

Owner publication creates a snapshot of the current eligible authorised set. A per-publication row lock serialises version allocation and identical simultaneous requests reuse one version via a unique fingerprint. New authorised images require publishing a new version. Each image gets `UUIDv5(publication UUID, private submission UUID)`: stable within that dataset across versions, different across datasets, and not a contributor/account identifier. ZIP paths are `images/<dataset-image UUID>.png` only.

Snapshot membership and public annotations are immutable once its build record is created. This boundary applies before generation, so a queued version cannot grow silently. The first completed manifest and archive SHA-256 become immutable. Cache regeneration must reproduce the exact manifest, image hashes and ZIP checksum, or fail closed. Fingerprints include selected annotations, consent references, export format revision, pinned encoder version and licence-text hash. Changes to packaging semantics require an explicit export-format revision bump in the snapshot fingerprint; old versions must never be silently rewritten.

ZIP contents:

- `images/`: decoded, metadata-free PNG conversions, generated one image at a time. Input JPEG/PNG/WebP is validated and EXIF/GPS/XMP/text/ICC data is discarded. Source objects are never modified.
- `labels.csv`: dataset image ID, safe file reference, label key, selected answers and explicit public attribution. Multi-choice/boolean cells use JSON; CSV quoting is standard. Cells that could trigger spreadsheet formulas receive an apostrophe prefix; JSON retains the original structured values.
- `manifest.json`: dataset/version, collection, fixed export timestamp, count, criteria/schema versions, label definitions, selected question definitions, licence URL/ID, recorded permitted reuse, distribution/consent policy versions, processing/originality provenance and per-image references/checksums/labels/answers/public credits.
- `README.md`: description/purpose, version/collection references, use/attribution guidance, technical conversion and privacy/removal limitations.
- `LICENSE.txt`: the full standard licence text, with per-image attribution supplied in manifest/CSV.

No contributor email, account UUID, session/token, original filename, internal object key, private consent record or original GPS/EXIF is included. Public pseudonyms are supplied deliberately and reject email/URL-like syntax.

## Worker, limits, storage and recovery

The `datasets` Compose worker generates ZIPs asynchronously on a separate private `export_data` volume. Its source-image mount is read-only; the API's export mount is read-only. Only the worker writes cache files. Backend/worker use the same storage-port boundaries, without binaries in PostgreSQL. Environment flag `QPQ_DATASETS_ENABLED` defaults false, requires private uploads, and the existing local-storage gate prevents enabling this adapter in staging/production.

The worker takes a PostgreSQL advisory lock so there is one generator across worker processes. Builds have a five-minute lease; interrupted Building jobs can be reclaimed after lease expiry. Cache files use generated UUID paths, bounded extensions, no symlinks, exclusive creation and atomic final rename. Fixed ZIP timestamps, permissions, entry order and PNG encoding make regeneration deterministic. No client filenames/paths enter the archive.

Limits: 500 images per snapshot, 512 MiB per ZIP, 32 MiB per canonical PNG, 24 MP and 10 MiB per source, 120 seconds checked between images, 8 KiB of public annotation data per member and 2 MiB per snapshot, 4 MiB manifest, 2 MiB CSV, 1 GiB aggregate cache with conservative space reservation. One in-progress image encode is additionally bounded by pixel/memory/CPU controls; the time limit is not a preemptive decoder sandbox. Compose caps the generator at one CPU and 768 MiB. Requests return queued/failed state rather than building a ZIP in the web process. A resource-limit failure never exposes a partial ZIP.

Cached ZIPs expire after 15 minutes. Expired downloads return 410 and can be prepared again without creating a new version or charging credits. Successful regeneration resets the consecutive-failure count; three failures impose a 15-minute retry cooldown. Source/object or encoder changes that violate a fixed snapshot fail closed. Cleanup removes expired/revoked artifacts and old orphan/temporary files, while keeping version, membership and consent audit rows. A removed/missing cache file can be queued again. No existing image volume is deleted or reset.

Direct authorised streaming is used instead of bearer links: no download secret appears in URLs. The API requires an active explicit public policy, non-revoked immutable version, currently eligible members and an unexpired ready artifact. It checks eligibility again before every 256 KiB chunk and stops at cache expiry. HTTP Content-Length lets clients detect truncation instead of accepting an incomplete ZIP. The backend permits four concurrent streams per process and closes/reclaims stream resources on completion/disconnection. The Next transport streams the response rather than buffering it and forwards no permanent public object-storage URL.

Backend PostgreSQL rate buckets cover browsing (300), preparing (20), downloading (30), public reports (10) and owner snapshot requests (20), each per actual peer per **15-minute** window. Caller-supplied forwarding headers are not trusted. With the current Next proxy, browsers share its backend peer bucket; deployment needs a reviewed trusted-proxy/global rate policy before widening these limits. No throttle is a credit-ledger write.

## Removal, legal restriction and reports

Database triggers atomically revoke every affected version when a source is hidden/deleted, a removal request is inserted, a contributor/owner withdraws image distribution, or the publication is withdrawn. The worker cannot mark a revoked build Ready: final validation locks source rows before the version, matching removal lock order. Active downloads stop before their next chunk after a committed restriction. Previously sent/in-flight bytes and **previously downloaded copies cannot be remotely revoked**. Blocking further QPQData access does not claim to rescind irrevocable rights already validly granted under an open licence.

Old ZIP files can remain briefly on the private volume until cleanup, but the API denies them immediately after the restriction commits. They are never served as static/public files. New versions exclude restricted members; old versions stay revoked rather than shrinking silently. The Phase 2D image-deletion and retained-credit policy is unchanged. Existing older removal requests remain grandfathered and their original private images are preserved.

Public visitors can send a bounded, rate-limited dataset/image report. Reports are private immutable queue records; owners see them in Dataset publication and use the existing review/removal controls or withdraw distribution. An unreviewed public report does not automatically destroy an image or establish a legal violation. Owners/operators must assess reports; there is no automated legal/originality determination or invented support-email address. Production publication requires staffed escalation, backup retention/erasure and review operations. The public report itself never deducts QC.

## Models, APIs and files

Migration `0008_datasets.py` plus frozen SQL adds `dataset_publications`, `dataset_consents`, `dataset_versions`, `dataset_members`, `dataset_builds`, `dataset_reports` (24 model tables total) and a project/status lookup index on submissions. Previous migrations/guards, records and credit rules remain unchanged. New triggers freeze snapshots/manifests/consents and revoke distribution on restrictions. No publication or consent is seeded.

Backend: `api/routes/datasets.py`, `schemas/datasets.py`, `services/datasets.py`, `services/dataset_exports.py`, `integrations/exports.py`, `jobs/datasets.py` and bundled licence resources. Existing app assembly/config/health/models are extended, with no ledger posting path in these services.

Public API: `GET /api/v1/datasets`, `GET /datasets/{id}`, `POST /datasets/{id}/versions/{number}/prepare`, `GET /datasets/{id}/versions/{number}/download`, `POST /datasets/{id}/reports` (all under `/api/v1`). Owner API: collection `/dataset` GET/POST; dataset `/review`, `/reports` GET; `/images/{submission}/authorise` or `/withdraw`; `/versions` POST and `/withdraw` POST. Contributor API: submission `/export-consent` GET/POST and `/withdraw-export` POST. Mutations require the configured Origin; account mutations also use existing verified/eligible sessions and CSRF. Public JSON inputs are bounded; response validation/errors do not expose payloads/secrets.

Frontend: `/datasets`, `/datasets/[id]`, protected `/collections/[id]/dataset`, dataset manager/download/report/consent components, same-origin `/api/datasets` transport, and regenerated API types. The profile menu remains unchanged. No payment, credit purchase or marketplace feature is introduced.

## Manual end-to-end verification

1. Preserve `.env` and existing volumes. Set `QPQ_DATASETS_ENABLED=true` locally alongside the working development auth/upload flags. Run `docker compose config --quiet`, then `docker compose up --build -d --wait --wait-timeout 180`. Check API, frontend, database, Mailpit, cleanup, notification and dataset workers; migrate/dev-seed must exit 0. `docker compose exec -T backend .venv/bin/alembic current` should show `0008 (head)`.
2. Use two separate browser profiles for owner and contributor. Sign in with their existing Mailpit links, or create fresh `owner-2e-<unique>@university.test` / `contributor-2e-<unique>@university.test` accounts. Open links in the requesting browser profile. Never reset a balance or award another welcome grant to an existing account.
3. Owner: create a complete collection with a supported standard licence/reuse terms, target 3 and reward 1 QC, at least one image label, one structured question and one private short-text question. Publish. Contributor: submit two synthetic/original non-identifying images, answering both questions. Owner: approve the first image, leaving the second Pending. Record both wallets **after** this ordinary payout. Approval alone must not list a dataset or enable a download.
4. Owner: My Collections → Dataset publication. Select the structured question; note that text questions cannot be selected. Read and explicitly confirm the publication/rights/privacy policy. Before contributor opt-in and owner image authorisation, publishing a snapshot must fail as empty.
5. Contributor: My Submissions → Optional public dataset distribution. Read the licence, terms and public-field list. Use a public pseudonym for BY/BY-SA, never an email. Explicitly opt in for the approved image. Pending images may opt in but still cannot be authorised/exported until approved; rejected images cannot opt in.
6. Owner: refresh Dataset publication, inspect the approved image, its public answers and attribution, confirm the separate per-image rights/privacy review and authorise export. Click **Publish current image set as a version**. Retry the same action: it should reuse version 1, not duplicate membership. Wait for the worker and refresh availability.
7. Guest browser: open `/datasets`, search/filter by name/category/licence/collection UUID and open the details. Confirm purpose, labels, selected schema, licence/reuse terms, criteria version, image count 1 and **Free · 0 QC**. Read the licence checkbox and download version 1. No login or QC balance is required. Check that only the authorised approved image is present.
8. Extract the ZIP locally. Verify `images/`, `labels.csv`, `manifest.json`, `README.md`, `LICENSE.txt`; confirm stable image IDs, count, label/structured answer, licence and public pseudonym. Ensure private text, account emails/IDs, object keys, original filenames and GPS/EXIF are absent. Compare manifest hashes to image files if desired (`shasum -a 256 images/*.png`). Re-check both wallets: downloading/prepare/report must change no available/reserved balance or ledger history.
9. Owner: approve the second image. Contributor opts in; owner separately authorises it and publishes the current set. Version 2 must contain 2 images. Version 1 stays byte-for-byte and manifest-for-manifest unchanged, containing 1 image. A Pending/rejected/unconsented image must never enter either export.
10. Wait for a 15-minute cache expiry. Direct download should return 410; acknowledge the licence and prepare the same version again. Refresh after generation. Re-downloading should produce the same SHA-256 and fixed manifest/export timestamp. No extra QC is charged. Do not alter immutable timestamps to force this manual test.
11. Contributor: withdraw export consent for the first image, or owner withdraw its distribution permission. Both versions containing it must immediately become unavailable. Original submission/image status and QC remain unchanged. Publish a new snapshot from still-authorised images; it must exclude the withdrawn image. Alternatively, use the existing image removal request to verify private image suppression and version revocation together. Keep downloaded copies only as synthetic test artifacts; QPQData cannot recall them.
12. Guest: send a dataset/image concern through the details form. Owner: inspect it in Dataset publication and take the appropriate review/removal/withdrawal action. Another account must not read the report queue, authorise images or create versions for that collection. Whole-dataset withdrawal must remove it from the library and block its existing downloads permanently.
13. Optional fault/retry checks: stop only the dataset worker, queue a version, confirm the web application stays responsive and shows Queued; restart it and refresh. Interrupt a browser download and retry while the cache remains valid. Oversized snapshots/ZIPs must fail without exposing a partial archive. Use automated synthetic tests for mid-generation/mid-stream removal and resource bounds; do not delete existing image objects or weaken guards to manufacture failures.

See [verification.md](verification.md) for actual executed results and remaining manual/device checks. Stop after Phase 2E for review.
