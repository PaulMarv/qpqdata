# Authentication — Phase 2A

On 30 October 2026 the user explicitly selected **passwordless email-link authentication** for the MVP. Email-and-password login is not required. The implementation specification and acceptance steps are in [phase-2a.md](phase-2a.md).

Email verification and login have separate purposes. Existing development verification tokens retain their purpose and UI. Login links are valid for exactly ten minutes, single-use, stored only as hashes, and bound to the initiating browser. The common token store and SMTP delivery are reused; a verification token cannot be exchanged through the login flow. Explicit POST confirmation prevents GET/link-scanner consumption. Tokens are removed from URL fragments after loading, never saved in localStorage and never logged.

Sessions are opaque server-side records, not browser JWTs. Session and CSRF cookies are HttpOnly, SameSite=Lax, Path=/; outside loopback development they are Secure and use __Host- prefixes with no Domain attribute. Backend absolute/idle expiry, revocation, account enablement and current organisation eligibility are checked on every protected request. Logout revokes the session in PostgreSQL; reauthentication rotates it. BFF Origin checks and backend Origin plus session-bound CSRF checks protect mutations. Protected response data is not cached.

Mailbox control does not establish current school/work affiliation. Real accounts require an exact reviewed school/university/employer domain and current independently reviewed membership evidence; no `.edu`/`.ac.uk` suffix shortcut is used. The development fixture exception is explicitly confined to university.test in development. Reserved test domains and copied development markers are denied elsewhere. Production email verification can commit an account awaiting review, but cannot issue a session or welcome grant until eligibility is established. No reviewer authentication or automated organisation approval is introduced in this phase.

The verified eligible user's welcome grant is one append-only 50 QC ledger entry, with a canonical per-user idempotency key and an independent database uniqueness rule. Challenge consumption, account activation, welcome posting and session creation share the transaction. Failure rolls back the whole activation. Existing balances remain ledger-derived. Future credit activity cannot be implemented as a balance mutation.

Account identity remains issuer plus subject. The development email issuer is preserved; real mailbox identities use a separate email issuer. Existing federated accounts are never silently linked using email. OIDC/federation and higher-assurance methods remain possible future integrations, not dependencies of this MVP. Email changes, password storage/reset, image features, collection workflows, transfers and social login are outside Phase 2A.

Auth is explicitly enabled locally. Production defaults remain disabled and require configured HTTPS/STARTTLS transport, a real sender and reviewed organisation/membership operations before activation. No external credentials are invented. See [development-email.md](development-email.md) for the preserved Mailpit harness and [phase-2a.md](phase-2a.md) for deployment limits.

Security choices were checked against the [OWASP session-management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) and [OWASP email-verification guidance](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html).
