# Phase 2C — Capture, labelling and submissions

## Scope and inspected foundation

Phase 2B collection UUIDs, immutable published definitions, authentication/eligibility, append-only ledger and reservation rules are retained. The existing models, migrations 0001–0004, auth/CSRF/session dependencies, API transport, collection UI and tests were inspected before implementation. No frozen earlier migration is rewritten. New migration **0005** adds submission provenance/image attributes and an append-only removal-request queue. No real user or photograph is seeded. No moderation decisions, contribution payouts or ZIP/download publication are enabled.

FastAPI owns admission, answer/content validation, upload completion, private access and consent. Next.js provides the mobile-first presentation and same-origin authenticated transport. The recent blue/ink theme and locally hosted typography are reused.

## Workflow and policies

1. An authenticated, verified, currently eligible contributor reads the complete collection definition and privacy warning.
2. Separate camera and gallery file inputs support device-native capture (`capture=environment`) and multiple gallery selection. Gallery never invokes `getUserMedia` or requests camera permission. Unsupported capture browsers fall back to their file picker. HEIC, GIF, SVG and animated images are unsupported; export HEIC as JPEG. The document permits same-origin camera use, while microphone/geolocation remain disabled.
3. Up to **5 images per batch** have independent preview, remove, replace/retake, label and question state. Object URLs are revoked on removal/replacement/unmount. Cancelling a replacement picker retains the original preview. Client checks improve feedback; backend checks remain authoritative.
4. Each image has one collection label and answers generated from the frozen published criteria version. All five field types and required/optional rules are validated on the backend. Unknown keys, invalid choices, repeated selections, wrong primitive types, non-finite/out-of-range/non-integral numbers, whitespace-only answers and invalid text/selection lengths are refused. Required `false` and numeric zero are valid values. Numeric answers are bounded to ±10^15.
5. The review screen shows every image's own label/answers and the collection licence/reuse text. The contributor explicitly confirms ownership/permission and privacy/copyright review; both must be JSON `true`, not truthy strings/numbers. No automatic check is represented as proving originality, ownership, privacy or copyright compliance.
6. A per-image initiation request reserves a capacity slot for **15 minutes** and stores the immutable definition version, label key, answers and server-generated consent record. The browser-generated UUID retry key is unique per contributor; identical retries return the same record. Reusing it with another project or different metadata returns 409.
7. Raw bytes upload separately, with per-image progress and a validating/saving state. Successful validation/storage atomically changes Uploading → **Pending Review**. Failure leaves the same slot retryable until expiry. Successful siblings are not retried. My Submissions can recover an unfinished upload from a newly selected file or discard its slot. Metadata for that slot cannot change; discard/start a new request to change answers.
8. Confirmation and My Submissions show IDs, frozen definition version, answers/consent, status and authorised private thumbnails. No QC is earned by submitting in this phase.

Admission requires a published, unexpired collection with a live QC reservation; self-contributions are forbidden. Pending/approved records and unexpired, non-abandoned upload slots count against the image target. At most **20 active/completed images per contributor per collection** and **5 active upload slots per contributor per collection** are allowed. Rejected records would free capacity in a later reviewed moderation phase. Hidden pending images still retain capacity and funding until their review/removal is resolved. Collection-row locks and database guards serialize capacity admission. Eligibility, state, expiry and metadata are checked again when bytes are completed, so pausing during an upload prevents a new pending submission.

Previously completed identical-image retries may return their original pending record even after pause; this admits no new contribution. First-time uploads and new manifests are refused on paused/closed/expired projects. The exact normalized decoded pixel hash is unique per contributor and collection. It catches identical content and metadata-only variants, not perceptual similarity, edited copies or every lossy recompression. A duplicate under a fresh retry key leaves an unfinished slot that can be discarded or allowed to expire; it cannot create a second pending image.

## Funding and lifecycle boundary

No ledger entries are posted by contribution endpoints. Existing welcome grants/reservations are untouched. Pausing/resuming a funded collection with pending images is supported. **Closing/releasing the reservation is blocked while pending/approved images or live upload slots exist**, including through a direct database attempt with an otherwise correct refund. Owners may pause to stop new work. Discarded/expired slots alone do not block close. Moderation/reconciliation must be reviewed in a later phase before releasing funds for outstanding work.

The schema recognises Uploading, Pending, Approved and Rejected. New records must begin Uploading, and only Uploading → Pending is enabled. No API accepts a status field or moderation decision. PostgreSQL rejects direct Approved/Rejected transitions and changes to completed metadata/image provenance. Consent, criteria version, request hash and submitted answers are immutable. Abandonment and privacy suppression are one-way flags, not moderation decisions. Legacy Phase 1 rows retain null workflow markers and all prior values; they cannot be silently reinterpreted or edited through the new API.

## Private storage and processing

The `ObjectStore` port has put/read/delete operations; `LocalObjectStore` supplies the development implementation. A production object adapter can replace it without changing image metadata/provenance contracts. **Uploads fail closed in staging/production**: this phase intentionally enables only development/test filesystem storage, with no invented cloud credentials or public bucket. A production adapter, deployment review, restricted database role and storage lifecycle policy remain required.

Local objects live only in the backend/cleanup-worker named `image_data` volume at `/app/private-images`, outside Next.js public/static paths. PostgreSQL stores opaque references, hashes, dimensions, encoded size, format and submission/consent metadata; never image binaries. Only server-generated UUID object keys match the adapter's strict grammar. Absolute paths, traversal and symlinks are refused; files are exclusive-created with mode 0600, directories 0700. No original filename is used as a path or persisted. Runtime containers use the existing non-root UID.

Each upload is limited to **10 MiB**, **24 megapixels**, at most 20,000 pixels on an axis, a single frame and the collection's actual JPEG/PNG/WebP allowlist/minimum oriented dimensions. A decoder format allowlist, full load and bounded image-size check reject unsupported, truncated or oversized files. Pillow 12.3.0 is the only new locked dependency. EXIF orientation is applied, then fresh RGB/RGBA pixels are encoded in the detected accepted format; no EXIF/GPS/XMP/ICC/text payload is copied. JPEG/WebP re-encoding is lossy (quality 90); there is no resizing. Colour profiles are not retained, so this is not a colour-managed archival ingestion pipeline. Originals are never written to disk/object storage. File validation cannot find visible faces, addresses, documents or copyrighted content.

Limits apply before decoding and after encoding. Upload stream reads have a 30-second budget, four active receivers per backend process, two concurrent decoders per process and a 40-attempt/minute authenticated user throttle for valid upload slots. JSON manifests are limited to 64 KiB. The Next transport streams a bounded request and enforces declared/streamed limits; backend limits also apply to direct callers. Compose bounds backend memory to 1536 MiB. These controls are not a production processing sandbox: production requires patched decoder monitoring, process/CPU/memory isolation and reverse-proxy rate/size/time limits. See [Pillow security guidance](https://pillow.readthedocs.io/en/stable/handbook/security.html).

Private images are read through an authenticated endpoint authorised for **the contributor only** in this phase; collection owners/public users cannot inspect them. No owner moderation inbox is enabled. Responses use generated image MIME types, nosniff and no-store. Browser image URLs are authenticated application routes, not permanent public object URLs or bearer links. Next.js image optimisation/CDN caching is intentionally bypassed for private/blob images. No tokens are stored in localStorage or URLs.

## Failure recovery and cleanup

Database transactions hold the submission lock through object write and metadata commit. A failed write/commit is rolled back and the attempt object is removed when possible. Crashes can leave unreferenced sanitized objects; cleanup reclaims only unreferenced files older than **one hour**. It locks the matching submission row before checking its committed reference, serializing against writers so a long commit cannot lose its object. Referenced images, including hidden ones awaiting review, are preserved. Empty attempt directories are removed where possible. No original image temporary files are created.

The `upload-cleaner` Compose worker scans every 60 seconds, marks expired Uploading slots abandoned and sweeps orphan files. Its healthcheck uses a recent successful-scan heartbeat. It logs counts/generic failures only; no credentials, tokens, paths or image/answer payloads. A one-shot scan can be run with `docker compose exec upload-cleaner .venv/bin/python -m app.jobs.upload_cleanup --once`. The worker does not remove submission/consent/ledger rows or decide moderation/removal requests. A discarded/expired row remains as audit history and cannot be reopened. Retry the same slot before expiry; after expiry, start a fresh contribution with new consent/key.

## Privacy reporting / minimum moderation mechanism

My Submissions → **Report a concern / request removal** records privacy, copyright or other concerns in `removal_requests` with actor, timestamp and bounded details. The first request and suppression timestamp are immutable/idempotent. Image access is hidden immediately; consent/provenance and the private object are retained pending human review. This is suppression and an operator queue, **not a completed physical-erasure or copyright decision**. No automated notification is sent to third parties.

Minimum operator procedure before any public pilot:

- Assign a responsible operator and a published support/removal contact. This repository does not invent a support address or notification service. Requests from users who lost institution/session access must be accepted through that operator channel after identity/ownership review.
- Review queued `removal_requests` using a controlled, authorised read-only database inspection; restrict its potentially sensitive text. There is no moderator UI/API in Phase 2C. Review promptly and document actor, evidence, response and applicable retention/legal obligations in the organisation's approved case system.
- Keep suppressed images excluded from all future owner review, exports, datasets and payouts until a reviewed policy resolves them. Do not restore access by manually clearing flags or bypassing triggers.
- Physical object/backup erasure, status changes and any credit reconciliation require a separately reviewed administrative procedure/migration. Do not manually mutate the append-only ledger. Establish retention and deletion deadlines before real photographs are accepted publicly.

Do not use this local implementation as a publicly operated dataset service before those operational measures and moderation/security review. Automated file validation never certifies originality or privacy.

## API / file map

| Method | Endpoint | Purpose |
| --- | --- | --- |
| POST | `/api/v1/projects/{project_id}/submissions` | Eligible contributor; consent/answers/version and idempotent upload slot |
| PUT | `/api/v1/submissions/{id}/image` | Authenticated CSRF-protected bounded raw image upload; Pending on success |
| GET | `/api/v1/submissions` | Contributor's server-paginated records (default 10, max 50) |
| GET | `/api/v1/submissions/{id}` | Contributor's metadata/consent only |
| GET | `/api/v1/submissions/{id}/image` | Contributor's unsuppressed pending private image |
| POST | `/api/v1/submissions/{id}/cancel` | Abandon own incomplete upload, idempotently |
| POST | `/api/v1/submissions/{id}/removal-request` | Record own concern and suppress access |

- `backend/app/api/routes/submissions.py`: auth/CSRF and explicit transaction boundaries, streaming and private HTTP responses.

- `frontend/src/app/components/contributor.tsx`, `image-labels.tsx`, `submission-card.tsx`: capture/selection, per-image forms/review/progress and personal records/recovery/removal.

## Local setup and manual acceptance

Keep the existing `.env`, database and volumes. Do not use `down -v`, reset the database, rewrite migrations or run tests against the development database.

1. Set `QPQ_ENVIRONMENT=development`, `QPQ_AUTH_ENABLED=true`, `QPQ_DEV_EMAIL_ENABLED=true`, `QPQ_UPLOADS_ENABLED=true`, `QPQ_FRONTEND_URL=http://localhost:3000` in the existing local `.env`. Root examples leave uploads false by default. Run `docker compose config --quiet`, then `docker compose up --build -d --wait --wait-timeout 120`. Check db/backend/frontend/Mailpit/upload-cleaner healthy and migrate/dev-seed exited 0. `docker compose exec backend .venv/bin/alembic current` should show 0005. The new image volume must remain private and persistent.
2. For host development, also set `QPQ_UPLOADS_ENABLED=true` in frontend `.env.local` and backend shell configuration. Set backend `QPQ_STORAGE_ROOT` to an absolute writable directory outside frontend/public and Git (e.g. `/tmp/qpqdata-private-images`). Start the cleanup module in that same environment. Compose already sets these paths/worker automatically.
3. Use an owner account and a different contributor account. Register/log in via `/signup` or `/login`, open http://localhost:8025, open that mailbox's link in the requesting browser and explicitly confirm. Fresh exact `university.test` addresses are supported locally; existing accounts and actual balances are retained. Use separate browser profiles/incognito sessions for owner and contributor. Do not copy secret links into screenshots/logs.
4. As owner, create a complete collection with enough QC, labels Clean/Messy and all five question types, including a required choice, optional text, bounded whole number, multiple choice and yes/no. Choose accepted JPEG/PNG/WebP formats, minimum dimensions, licence/reuse terms and optional future closing date. Publish and record the reservation. The owner must be refused contribution to their own collection.
5. As a guest, open its details and read requirements. Contributing requires login. As the other eligible user click **Contribute images**. Review instructions, labels, licence, format/dimension rules and privacy warning; continue.
6. **Choose from gallery**: select two synthetic/original non-sensitive supported images. No camera prompt should appear. Verify independent previews, remove, replacement and that cancelling replacement keeps the old preview. **Take a photo** on a supported phone should open its device capture flow; Retake replaces that photo and clears its old answers. Desktop/browser fallback may be a file picker. A real-device camera check is manual and is not claimed by component/desktop tests.
7. Local Compose is loopback-only. Use desktop responsive emulation for layout; for an Android physical-device test, an already configured USB debugging setup can forward device localhost ports (`adb reverse tcp:3000 tcp:3000`, and 8025 for Mailpit). Request/verify the login in the phone browser so its nonce matches. Do not expose unauthenticated Mailpit or relax the development frontend-origin gate to test on a LAN. iOS capture requires an appropriate secure device development setup; production remains gated.
8. Try HEIC/GIF/SVG, empty or >10 MiB files and more than five selected images: expect clear selection errors. Try a renamed/corrupt image that passes browser heuristics: backend must reject actual bytes. Try below-minimum or >24 MP images: backend must reject, with no Pending record. Originals must never appear in storage.
9. Give the two photos different labels and answers. Required missing answers must block Review. Test duplicate/unknown choices, too many/few selections, too-long text, fractional whole-number answers and values outside bounds. A required No/false and zero must work. Review must show each image's own values and current published definition version.
10. Submit is disabled until both ownership/licence and privacy confirmations are checked. Submit and observe upload percentage, validating/saving, then **Submitted · Pending Review**. No Approved/Rejected selector or payout appears.
11. In My Submissions inspect private thumbnails, IDs, version, labels, answers and retained consent/licence. Open the image URL in a guest or another account: it must be denied (even the collection owner in this phase). Confirm it has no-store/nosniff and no public storage URL. Download/inspect your authorised sanitized test image locally with an image metadata viewer: EXIF/GPS/text should be absent. Automated tests use synthetic GPS/author/orientation/PNG-text fixtures.
12. Simulate a network interruption during upload or interrupt the current request, then retry the failed image. The same slot/request key is reused, completed siblings are not resent, and there is only one pending record/image for that content. My Submissions can reselect a file to recover an Uploading record. Discard an unfinished upload to free capacity. After 15 minutes it must expire; a retry requires starting a fresh contribution. Run the cleanup one-shot if inspecting expiry/orphans.
13. Submit identical content with a fresh key: duplicate completion must fail. A different photo can use the unfinished slot before expiry; discard it if unwanted. Collection capacity includes pending images plus active leases, so two users racing for the final slot must not both succeed. The integration suite covers exact concurrency, the five-slot limit and 20-image contributor limit; use a funded synthetic collection if testing those manually.
14. Owner pauses: new initiation/completion must fail. Owner resumes: existing pending images remain intact. Closing while pending/live slots remain must fail and keep the reservation. Closing a collection whose only slots were discarded/expired may release its reservation. Confirm contributor QC is unchanged and no contribution payout ledger entry exists.
15. In My Submissions → **Report a concern / request removal**, choose privacy/copyright/other and optional details. Submit: the image is hidden immediately and the queue record is retained. Repeating the request must not duplicate it or restore access. This does not erase the object or decide rejection; follow the minimum operator procedure above.
16. Sign out and confirm private pages/images fail. Revoke eligibility in an isolated synthetic integration fixture (not by editing real accounts) and verify contribution fails. Review phone layouts, keyboard focus, labels, focus rings, progress announcements and error recovery before accepting Phase 2C.

Run the existing README commands for all locked backend/frontend checks. PostgreSQL integration requires a new disposable empty database; never set TEST_DATABASE_URL to the development database. Actual executed results and limitations are recorded in [verification.md](verification.md).

Stop after Phase 2C for review. No moderation decisions, payouts or dataset ZIP downloads are authorised by this implementation.
